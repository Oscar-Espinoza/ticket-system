# Inventory: routes, loads, build scripts, tests (non-api)

## Structural findings (max 25, most important first)

**A. Auth/membership is re-done in every load instead of once in a layout**
- [hidden] src/routes/dashboard/+layout.server.ts:20, src/hooks.server.ts:66-73, src/routes/dashboard/**/+page.server.ts — The signed-in check exists three times: `dashboardGuard` in hooks (full-page only; skips `isDataRequest`/`isRemoteRequest`), the dashboard layout load (`redirect(303,'/login')`), and again in 54 page loads (`grep "redirect(303, '/login')"` under routes, non-api) in two spellings (31x `getSession()`, 24x `locals.user`). A layout load does NOT protect page `__data.json` requests (layout and page run in parallel), so the per-page copies are load-bearing only because the pattern is "each page re-checks"; hooks.server.ts:62 comment says so. Forgetting one line is a silent auth hole. Change together: every new page.
    Fix idea: one guard in `handle` that covers data requests too (return 401/redirect JSON for `isDataRequest` under /dashboard), then pages read `locals.user!`; delete the 54 per-page redirects and the `getSession()` spelling.
- [hidden] src/routes/dashboard/projects/[id]/+layout.server.ts:26 vs ~23 page loads — Layout returns `projectData` (membership-gated, 404 for outsiders), then pages repeat the gate: `getProjectData` in triage/cycles/cycles/[cycleId]/insights/epics/[epicId]/views/issues/[key]; `getMemberProject` (a different query: project-access.ts:162) in 14 settings pages; or nothing and rely on the SQL membership join (archive, trash, roadmap, customers, docs, epics). Same question ("is viewer a member?") answered by 3 mechanisms, each page comment says "layout already checked" yet re-checks. Same race caveat as above (page data requests run in parallel with the layout load) is why they do it, but it is undocumented per-page folklore.
    Fix idea: pick one rule (page loads call a single `projectMember(event)` helper that reuses the memoized `getProjectData`) and apply it everywhere; drop `getMemberProject` from settings loads.
- [special:copied] 14 settings loads (e.g. settings/labels/+page.server.ts:15-20, sla:15-22, workflow:14-20, automations, planning, intake, github, integrations, developer, general, members, templates, recurring, audit) each repeat: params.id → auth → `getMemberProject` → `error(404)` → return `{projectId: id, ...canEdit: roleAllows(role,'write'|'admin')}`. `projectId`/`projectName`/role are already in the layout's `projectData.project` (use via `useProjectData()`), so 20 loads return `projectId: id` redundantly (`grep "projectId: id"`). The per-page minimum role is a literal in each load, away from the nav entry in app-shell/routes.ts (`PROJECT_SETTINGS_NAV`).
    Fix idea: `settingsLoad(minRole, fn)` wrapper, or a settings `+layout.server.ts` that returns `{role}` once.
- [needless] 26 route files import `@/lib/db` + drizzle directly (list: `grep -l "@/lib/db" src/routes`), e.g. settings/sla:7-11 selects one column of `projects`, settings/automations, planning, intake, general, github, workflow, labels, members, developer, integrations. Routes are the most volatile layer yet embed schema columns; the same column sets are likely re-read by the save actions in src/lib/server/actions/*.
    Fix idea: one `project-settings-read.ts` in lib returning the typed settings slice per tab; loads become 3 lines.

## Cross-area observations

- src/lib/server/actions/*.ts (~35 files) import the no-op `revalidatePath` purely as a generator marker for scripts/gen-remote-actions.mjs; the contract lives in a regex in the script, not in types. See the generated wrappers area (src/lib/remote, src/lib/actions).
- src/hooks.server.ts:66 dashboardGuard + :69 `isDataRequest` exemption is the real reason pages re-check auth; any auth redesign must start there (api/auth agent's area).
- src/lib/project-access.ts header (lines 1-30) still documents `requireProjectMember` / "Server Component → notFound()" Next conventions; `getMemberProject` vs `getProjectData` (src/lib/project-data.ts:29) overlap as membership checks.
